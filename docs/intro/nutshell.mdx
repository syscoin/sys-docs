Syscoin is a Bitcoin-merge-mined blockchain with its own rules for asset transfers, data publication, and programmable settlement. Its design lets people and autonomous agents act through independently operated applications while sharing a history they can verify for themselves. [Core and merge-mining](../architecture/core.mdx#what-bitcoin-merge-mining-contributes) · [System architecture](../architecture/overview.mdx)

**Why build on Bitcoin mining?** A participating pool can use the same hash attempts to compete for BTC on Bitcoin and SYS on Syscoin. Bitcoin validates its own blocks. Syscoin’s nodes validate the additional transactions, data commitments, and settlement rules. SYS pays for using those services and helps fund the operators who provide them. zkSYS adds a separate reward token tied to SYS stake or eligible Sentry collateral. Whether the revenue attracts more independent operators depends on demand, costs, and who controls the equipment. [Follow the mining work and revenue](../architecture/core.mdx#why-bitcoin-and-syscoin-fit-together) · [Who pays whom](../architecture/modular-alignment.mdx#who-pays-for-the-shared-infrastructure) · [zkSYS issuance and fees](../architecture/zksys.mdx#sys-collateral-issuance-and-gas)

**Where it stands.** Core and its Ethereum-compatible settlement layer, NEVM, operate on mainnet. The post-quantum finality rules are a release candidate. zkSYS Genesis is a public testnet. The walkthrough below assumes those new finality rules are active and an enforcing verifier checks real execution proofs. [Network and release status](./status.mdx)

Syscoin’s 2021 scaling proposal began with a wallet holder’s problem. Keeping control of your coins is one requirement. Being able to spend them when an operator goes offline is another. Moving execution off the shared chain makes room for more applications, but it also means someone else must be able to recover the data and check the result. The same reasoning applies to an agent acting for a community. Who gave it the right to act, and what can a member verify after the operator is gone? [How the design developed, from the wallet holder’s problem to *Truth States*](../reference/research.mdx#from-a-computational-court-to-authority-over-scarce-resources)

## Follow the payment

Suppose your wallet sends a payment on zkSYS. It gets a local receipt. Later, someone who never used your wallet wants to check the result after the original operator has gone offline.

```mermaid
flowchart TD
    accTitle: How one wallet payment reaches shared settlement
    accDescr: The wallet authorizes a payment. The application executes it and issues a local receipt. After publication and proof checks under the active rules, shared settlement records the batch.
    Wallet["Your wallet authorizes a payment"] --> App["The application executes it<br/>and issues a local receipt"]
    App -->|"Publication and proof checks"| Settlement["Shared settlement records the batch"]
```

1. **Get a receipt.** An operator called a sequencer orders the payment on zkSYS and executes it. The receipt tells your wallet the local outcome. The batch containing the payment still has to reach shared settlement. [zkSYS transaction lifecycle](../architecture/zksys.mdx#follow-an-application-transaction)
2. **Inspect the publication.** zkSYS groups transactions into a batch and publishes its encoded data on Syscoin Core. A reader can retrieve each blob and hash it to check the batch’s ordered identifiers. After Core’s serving window, the reader needs an archive that kept those bytes. [Data publication and retention](../architecture/data-availability.mdx)
3. **Check which history counts.** Bitcoin miners can reuse their work to mine Core blocks. Under the post-quantum rules, a quorum of Sentry Nodes signs the block history, and Core nodes verify those signatures directly. A ChainLock gives readers a common finalized history in which to locate the batch publication. [Mining and finality](../architecture/core.mdx)
4. **Check the result.** A prover supplies evidence that the batch obeyed the execution rules. Identify the payment’s block and batch, then follow that batch to settlement on Gateway. Gateway settles its own batches on NEVM, Syscoin's Ethereum-compatible contract layer. To re-execute the blocks yourself, start from authenticated state and restore the replay inputs, including transactions, block context, protocol version and required preimages. [Proof and settlement](../architecture/zksys.mdx) · [Replay inputs](../architecture/data-availability.mdx#what-can-someone-verify-a-week-later)

The division of work lets zkSYS respond on its own schedule. Applications that join an Edgechain add execution work there. Their publications consume Core bandwidth and storage, and Core nodes validate blocks and check finality. [System map](../architecture/overview.mdx) · [Costs of independent validation](../architecture/design-tradeoffs.mdx)

Try the settlement check on a public Genesis testnet transaction. Follow its receipt to the Edgechain batch on Gateway, then find the Gateway batch on Tanenbaum NEVM. [Trace a public testnet transaction](../reference/zksys.mdx#trace-a-public-testnet-transaction)

## Where the other pieces fit

| Component | Purpose |
| --- | --- |
| [Core](../architecture/core.mdx) | Tracks balances as unspent transaction outputs (UTXOs). Accepts Bitcoin-compatible parent mining work through auxiliary proof of work (AuxPoW). |
| [Syscoin Platform Tokens and Z-DAG](../tech/tokens.mdx) | Let applications transfer assets directly as Core outputs. For eligible payments, wallets can ask a node for an early mempool conflict signal. |
| [Post-quantum ChainLocks](../architecture/post-quantum.mdx) | **Release candidate.** Authenticate Sentry operators with SLH-DSA hash-based signatures. Operators sign scheduled block votes with WOTS+ keys. |
| [Proof of Data Availability](../architecture/data-availability.mdx) | Publishes payloads through Core. Gateway can carry compact identifiers while independent readers retrieve and check the larger payloads. |
| [NEVM](../reference/nevm.mdx) | Runs Ethereum-compatible contracts, including verification and settlement contracts. |
| [zkSYS](../architecture/zksys.mdx) | **Public Genesis testnet and proof-settled design.** Executes on an Edgechain and settles through Gateway. Its reference contracts link reward eligibility to SYS and allow zkSYS to cover eligible fees. Inspect the verifier for the batch in question. |

To inspect the system yourself, query a Core block or retrieve a blob using the [command reference](../reference/overview.mdx). To evaluate the design, compare its costs with [other chains](../architecture/comparison.mdx) or inspect the real Bitcoin coinbase tags that the [proposed BTC bridge](../architecture/bitcoin-bridge.mdx) would use.
